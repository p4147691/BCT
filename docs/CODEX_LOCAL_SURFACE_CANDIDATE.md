# Local Codex surface candidate

This extends the isolated dot candidate; no runtime installation or live DB writes.
The supplied /local/client-new-thread:<UUID-shaped-reference> is observed as one
specific local Codex draft route. Its spelling is not proof of a real conversation,
Codex task ID, persisted thread ID, Work or CLI account. Other /local paths remain
unclassified. Existing /c/ chats with CODEX_MARKERS retain their N identity.

Registry module bct.codex_surface displays C1 through C99, then C1 again,
matching the existing N alias policy. Internal assignment sequence increases
independently of the cyclic display alias and independently of N assignments.
SQLite BEGIN IMMEDIATE plus unique reference/number constraints serialize concurrent
registration and make repeated same-reference registration idempotent. Existing
entries are not renumbered or deleted. Same reference in multiple tabs shares C;
instance/session/window/tab still identify each observed endpoint. Registration
does not grant execution authority. Different references do not inherit a number
merely because they occur in the same tab. Changes to the underlying task URL need
a separately verified identity transition before inheritance can be implemented.

Monitor first reads the existing read-only state, then explicitly POSTs unknown
fresh local Codex routes to the origin-checked registration endpoint. The BCT state
exposes codex_surface_directory and typed codex_nodes; ordinary current_nodes
remains the existing conversation-UUID contract. Cached unavailable observations
cannot allocate new C labels. The observed reference is not sent to the generic
UUID node-info, rename, send or return paths.

Monitor displays C<number> and Codex in the ordinary node presentation. The C
label means only an observed, confirmed local-reference form, not a BCT-routable
node or a claim that the work is private. Right-click Node Info exposes the local reference and
limitations. This draft's metadata fields are read-only because no
real task/Work mapping is established. Existing Codex CLI/account resource rows
are not merged with these browser drafts by title or apparent account name.

Verified locally: exact-route and unsupported-route boundaries, C persistence,
duplicate-tab C sharing, concurrent allocation, atomic invalid batch rejection,
read-only BCT state projection, HTTP origin/field checks, JS registration/display,
and headless Chrome Codex Node Info behavior (7 focused Python tests). Existing dot HTTP/SQLite browser
roundtrip and N node tests are rechecked. Real Codex task creation, route transition,
message delivery/return and loaded-extension acceptance remain unverified.

Read-only inspection now establishes a local persisted transition record: the current
Codex global state contains `client-thread-bindings-v1` entries from
`client-new-thread:<reference>` to UUID-shaped local task IDs. The active task had
one such binding, and the observed binding set had one unique task ID per reference.
This is evidence for a local app lifecycle association and for preserving a C label
when that exact reference is later associated with a task ID.

It is not a public or versioned Codex API, is not available through RCC, and does
not identify a ChatGPT `/c/` conversation or a send/return route. The candidate
therefore does not read this unsupported local store in Core, expose task IDs to Monitor, or
implement automatic task-ID/C-label inheritance. A future integration requires an
official/supported binding API or an independently versioned local adapter with a
fresh exact-binding proof and fail-closed behavior.

Existing N source evidence: conversation_network._next_node_number includes durable
assignment history; _node_label applies ((sequence-1)%99)+1. The existing
test_display_labels_cycle_after_ninety_nine_without_changing_identity covers this.
The policy does not skip a displayed alias that is still in use: the first and
100th references may both display C1. Their reference, assignment sequence and
exact tab endpoint remain different. C aliases must never be used as unique send
targets. This candidate exposes no send-by-C command. Reopening the same local
reference preserves its assignment sequence and cyclic alias.
