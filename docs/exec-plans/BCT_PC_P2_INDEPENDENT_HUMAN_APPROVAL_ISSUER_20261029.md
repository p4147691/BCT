# BCT P2 독립 사용자 승인 UI / 서명키 경계 — 인계 (2026-10-29)

## 구현·권한 경계

- 기존 PR #347의 \`ApprovalVerifier\`(Ed25519 정확한 Principal/Work/Operation/target/요청 SHA/만료/1회 사용) 및 \`file_action_apply\`, \`process_stop_apply\`를 재사용했다.
- 신규 \`bct_approval_challenge\`: 읽기 전용 BCT Work·Operation 사전 준비. 승인 대상 능력도 해당 Work 액션에 포함되어야 한다. 실제 실행과 서명은 하지 않는다.
- 별도 프로그램 \`python -m bct.approval_issuer\`: Tkinter 사용자 승인 창이며 일반 BCT/MCP 도구 목록에는 추가하지 않았다. CLI로 \`--approve\`·\`--sign\` 등 자동 발급할 수 없다. 파일 선택→원본/대상/프로세스 모드·전문 검토→작업 ID 직접 입력→별도 암호 문구 입력→명시적 최종 확인→사용자 지정 경로에 1회용 \`.approval\` 발급.
- 이 프로그램은 자체 HTTP 서버·원격 명령·BCT API 발급 엔드포인트를 열지 않는다. **일반 BCT 호출에는 개인키·암호 문구를 공급하지 않는다.**
- 사용자 개인키는 최초 GUI에서 Ed25519 새 키를 생성하고, 16자 이상 암호 문구와 scrypt 및 AES-256-GCM을 사용해 사용자 LOCALAPPDATA의 \`BCTApprovalIssuer/identity-v1.json\`에 암호화 저장. 키 덮어쓰기·무인 재발급 없음. 발급 시마다 암호 문구를 물으며 명령줄·환경변수·로그에 받지 않는다.
- 별도 승인 UI의 검증 공개키는 감독관이 **직접 육안 확인 후 운영 보호 정책에 고정**해야 한다. 서비스 자체가 공개키를 임의 대체하거나 정책을 승인 없이 활성화해서는 안 된다.
- 기존 \`[approval_verifier] enabled=false\` 기본값을 변경하지 않았다. 운영 BCT·RCC·Chrome·node-sync에 영향 없음.

## 정상 흐름

1. 사용자가 특정 파일 이동/복구 가능한 격리 삭제 또는 소유 프로세스 종료를 요청한다.
2. BCT는 파일 사전 계획/프로세스 신원 조사를 진행한 뒤 Work에 \`approval_challenge\`와 정확한 승인 대상 액션이 모두 있는지 확인한다.
3. \`bct_approval_challenge({work_id,operation_id,arguments:{capability:"file_action_apply",operation_id:"<실제 실행 Operation ID>",arguments:{...}}})\`를 실행해 정확한 정규화 요청 JSON을 받는다. **읽기 전용**이며 어떤 토큰도 만들지 않는다.
4. 사용자가 별도 사용자 승인 GUI를 직접 실행하여 JSON을 선택한다. GUI는 \`request_sha256\`을 요청 전문으로 독립 재계산하고 모든 파일 원본/대상 또는 프로세스 지문/종료 모드/Work/Operation을 표시한다.
5. 본인이 직접 확인/암호 입력/최종 승인을 눌러야 서명 토큰이 나온다. 거부·취소 시 어떤 토큰도 생성하지 않는다.
6. 실제 승인형 BCT 호출은 exact Work·Operation·요청 인자·서명 grant를 검증하고 nonce를 SQLite에서 단 1회 소비한 뒤에만 효과를 수행한다. 재시작/중복 실행은 기존 영수증을 재사용하고 UNKNOWN은 재실행하지 않는다.

## 안전한 운영 설정 조건

- 외부 발급 프로그램이 별도 인간 직접 사용 경계에 있다는 것, 사용자의 암호가 BCT 대화나 명령 인자에 절대 노출되지 않는 것을 확인.
- 운영 보호 경로/정책과 공개키가 일반 BCT 작업/코드 실행으로 수정되지 않도록 별도의 OS ACL·계정 격리를 검토. **같은 Windows 사용자 권한에서 실행되는 임의 코드와 키보드 후킹까지 막아 주는 OS 보안 경계는 이 구현만으로 제공되지 않는다.** 공격적 로컬 코드·관리자 권한에 대한 완전한 방호를 주장하지 않는다.
- Windows Hello·하드웨어 키 사용자 검증 또는 다른 격리 신원 수단이 요구된다면 별도 설계/승인을 완료할 것. 본 구현은 독립 GUI 및 사용자만 아는 암호를 신뢰 가정으로 한다.
- 공개키 등록, 정책 활성화, 실제 사람이 클릭하는 **물리 E2E**는 감독관 인수 후 보호된 테스트 장치에서 수행해야 한다. 테스트 자체가 사용자의 승인이라고 간주해서는 안 된다.
- 물리 승인 수락 전 Draft 유지 및 운영 기능 활성화 금지. 장애·키 분실 시 기존 발급 키 덮어쓰기·임의 회전 금지, 정책을 비활성화한 뒤 사용자 주도 절차로 복구.
