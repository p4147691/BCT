# Chain Direction V1

## 목적

`Chain Direction`은 1:1 Chain Message에서 B의 BA 보고를 받은 A가,
다음에 무엇을 할지 정리하는 부분 레시피다.

이것은 BCT가 판단을 대신하는 기능이 아니다. A가 원래 사용자 의도,
B의 보고, 영수증, 현재 확인값을 읽고 만든 **다음 지시 방향 기록**이다.

## 전체 위치

```text
사용자 의도
  → Chain Direction
  → Chain Message (상태 확인 · 실행 전 점검 · B용 작업 구성 · A→B 첫 전달)
  → B 내부: BB 반복 또는 BA 보고
  → A 결과 받기
  → Chain Direction
  → 필요하면 다음 Chain Message
```

`Delayed Send Message`는 B 내부의 BB 반복에 쓰는 부품이다. A가 BA 보고를
받아 다음 지시 방향을 정리한다고 해서 자동으로 필요하지는 않다.

## ABABA: 두 번 왕복하고 종료

사용자가 보는 `A → B → A → B → A`는 하나의 거대한 Chain Message가 아니다.
각 `A → B → A`는 독립된 1:1 Chain Message이고, 가운데 A가 끊지 않고 다음
Chain Direction을 만들어 두 번째 체인을 시작해 연결한다.

```text
A1 → B1
B1 → A2  (BA 보고)
A2 → Chain Direction(NEW_TASK) → B2
B2 → A3  (마지막 BA 보고)
A3 → Chain Direction(COMPLETE) → 종료
```

`A2`는 이미 B1의 보고 메시지로 깨어 있으므로, B2를 시작하기 전에 A 자신에게
Delayed Send를 보낼 필요가 없다. `A3`가 `COMPLETE`를 남기면 새 체인은 만들지
않으며, 이 2회 왕복 흐름은 끝난다.

## 입력: A가 반드시 읽는 것

```text
1. 원래 사용자 의도
2. 이미 합의된 목표·완료 조건·허용 범위
3. B의 이번 보고 전문과 BA 판단
4. B→A 전달 영수증 및 필요한 현재 확인값
5. 이전 A 판단과 아직 끝나지 않은 일
```

## 정리 결과: A가 남기는 방향

```text
현재 판단
  = 완료 / 보강 필요 / 검증 필요 / 사용자 확인 필요 / 보류

확정된 사실
  = 보고와 영수증으로 확인된 것

다음에 필요해 보이는 일
  = 원래 목표에서 자연스럽게 이어지는 후보

추정임을 밝혀야 하는 부분
  = 사용자가 원할 가능성은 높지만 아직 직접 요청하지 않은 범위

다음 B 지시의 범위
  = B가 이번 체인에서 해야 할 일과 하지 말아야 할 일

완료 조건
  = B가 돌아올 때 제시해야 할 증거와 종료 기준

사용자 확인 지점
  = 비용·시간·외부 변경·목표 확장이 필요한 경우
```

`현재 판단`은 A의 처리 기록이다. 다음에 실제 작업을 시작해야 하는 경우,
그 뒤에 새 Chain Message가 별도의 계획·전송 영수증을 남긴다. 판단 기록은
전송 성공을 뜻하지 않는다.

## 목표를 발전시키는 방법

A는 B가 지금 지시받은 범위를 완료했다는 사실과, 사용자의 궁극적 목적이
완료되었다는 사실을 구분한다.

```text
B의 범위 완료
  ≠ 사용자의 최종 목적 완료
```

A는 다음과 같이 발전 방향을 찾는다.

```text
원래 요청의 실제 사용 장면은 무엇인가?
현재 산출물은 그 사용 장면에 충분한가?
작은 검증 샘플은 전체 작업의 어떤 위험을 아직 남기는가?
다음 단계가 원래 목표의 자연스러운 연장인가,
아니면 새 권한·비용·외부 변경을 요구하는 확장인가?
```

이미 지정된 작업 범위·폴더 안에서 새 결과물을 만들고 검증하는 일,
그리고 원본을 보존한 되돌릴 수 있는 적용은 A가 진행할 수 있다.
문제가 없고 완료 조건을 충족하면 그 적용을 계속할 수 있다.

원본 교체·파괴적 변경은 금지한다. 처음 합의한 범위를 크게 벗어나거나,
되돌릴 수 없는 외부 영향·새 권한을 요구하는 일만 사용자 확인 또는
이미 합의된 권한이 필요하다.

## 대화망 준비를 포함할지의 판단

Chain Direction은 다음 Chain Message 전에 대화망 준비가 필요한지도 함께
판단한다.

```text
기존 A-B만으로 충분함
  → 대화망 준비 없이 바로 A → B

통합 작업을 한 창구로 모을 필요가 있음
  → 역할=supervisor인 노드를 찾음
  → 없으면 A가 기존 노드에 역할을 기록하거나 새 노드를 준비
  → 선택된 X에게 A → X

여러 대화를 같은 작업 범위로 묶어야 함
  → 대화망 구성·소속 설정
  → 바뀐 노드 정보를 확인
  → 선택된 X에게 A → X
```

`supervisor`는 역할 표지이며, 특별한 권한이나 별도 체인 종류가 아니다.
대화망 준비는 A가 필요하다고 판단했을 때만 전체 Chain Message 레시피에
붙는 선택 블록이다.

## 예시: TTS 번역 더빙

```text
사용자 의도
  일본어 원본을 자연스러운 한국어 더빙으로 쓸 수 있게 한다.

B 보고
  5~10초 비교 샘플에서 CER·클리핑·침묵 지표가 개선됐다.

A 판단
  샘플 품질 검증은 통과했지만, 전체 음원 더빙 완료는 아직 아니다.

A의 다음 지시 방향
  - 전체 원본 길이에 적용 가능한 파이프라인인지 검증한다.
  - 번역 의미·시간 정렬·화자 일관성·긴 구간의 침묵을 별도로 확인한다.
  - 원본은 보존한다.
  - 전체 파일 생성은 지정된 범위·폴더 안에서 별도 결과물로 진행할 수 있다.
  - 원본 교체는 하지 않고, 적용 전후의 되돌릴 수 있는 상태와 영수증을 남긴다.

다음 Chain Message의 B 완료 조건
  - 전체 적용 가능 여부와 남은 위험을 근거와 함께 보고한다.
  - 사용자 확인 없이 제품 자동 적용·원본 교체는 하지 않는다.
```

여기서 “사용자는 전체 음원을 원할 가능성이 높다”는 A의 **추정**이다.
샘플 성공만으로 전체 더빙 완료를 주장하지는 않는다. 다만 이미 지정된
범위 안의 전체 결과물 생성·검증은 진행할 수 있다.

## A 판단 뒤의 네 갈래

```text
완료
  → 1:1 체인 종료. 완료 근거를 남긴다.

검증 또는 보강 필요
  → Chain Direction → 새 Chain Message → B의 새 1:1 내부 반복.

사용자 확인 필요
  → 질문을 남기고 기다린다. Delayed Send는 기본값이 아니다.

보류
  → 이유와 다시 확인할 조건을 남긴다.
     시간·조건 감시가 정말 필요할 때만 별도 감시·알람·웨이크업 레시피를 붙인다.
```

## 아직 구현하지 않는 것

이 문서는 A의 판단 구조와 Chain Message의 입력 계약이다. BCT가 자연어를
읽어 목표를 자동 추정하거나, A의 판단만으로 새 메시지를 보내게 만들지 않는다.
그런 행동은 A가 새 지시를 실제로 작성하고, Chain Message가 별도의 전송
영수증을 만들 때에만 일어난다.
