# BCT 설계 기준

상태: 제안. 실행 코드와 마이그레이션 검증 전이다.

## 1. 관리 구조

사용자 설정의 진입점은 하나로 한다. 내부 책임은 core와 adapters로 나눈다.

- core: 요청 범위, 작업 상태, 공통 권한 결정, 변경 충돌, operation 식별.
- adapters: 파일/Git, 테스트/프로세스, 배포/서비스, RCC 등 기존 기능과 연결.
- settings: 사용자 정책과 가변 노드 속성. 버전과 변경 이력을 남긴다.
- runtime state: 실행 중 작업, 연결 세대, operation 결과. 사용자가 수동 편집할 설정과 분리한다.

명칭별 새 서버·레지스트리·정책 엔진을 만들지 않는다. 공통 판단은 같은 코드로 재사용한다. 원격 실행 경계의 인증은 유지한다.

## 2. 독립적으로 변경할 수 있는 신원

- node_id: UI와 작업 연결에 쓰는 안정적인 논리 ID.
- name, role, group: 변경 가능한 속성. 조직 역할이 기술 권한을 자동 부여하지 않는다.
- connection: 현재 tab/window/session 또는 MCP 연결과 generation. node_id와 별도다.
- execution principal: 실제 인증된 실행 주체. 표시 이름이나 node_id를 아는 것만으로 권한을 얻지 않는다.
- work_id / operation_id: 작업과 부작용 실행의 식별자. 노드 이름 변경에 따라 바뀌지 않는다.

탭·대화·창 중 어느 하나를 기술 권한으로 사용하지 않는다. 기존 ACT의 신원 규약은 adapter 경계에서 명시적으로 변환하며, 검증되지 않은 연결을 다른 주체로 승격하지 않는다.

이름 변경과 그룹 이동은 진행 중인 작업을 잃지 않는다. 연결 교체는 기존 응답이 새 연결의 응답으로 인정되지 않도록 세대를 확인한다. 실행자 교체는 진행 중 부작용과 인계를 확인한다. 만료 시각 하나만으로 이전 실행이 종료됐다고 판단하지 않는다.

## 3. 정책과 실행의 경계

공통 판단은 인증된 주체, 사용자 요청 범위, 대상, 위험도, 현재 충돌, 기존 operation 결과를 입력으로 받는다.

결과는 허용 / 승인 필요 / 차단으로 단순화하고 이유 및 필요한 다음 동작을 함께 반환한다. 영수증 기록은 별도 권한 종류가 아니라 부작용 operation의 공통 의무다.

사용자 지시 범위의 정상 작업에는 반복 승인을 요구하지 않는다. 삭제·인증 변경·복구 불가능한 덮어쓰기 등은 실제 요청과 위험에 따라 승인을 확인한다. 실제 동시 변경, stale HEAD, 불명확한 prior mutation은 추측으로 해제하지 않는다.

실행 직전 SHA, PID/fingerprint, 경로, 현재 연결 세대 및 원자적 충돌 검증은 실행기에 남긴다. 정책 결과만으로 이 확인을 생략하지 않는다. 모델은 추천을 제공할 수 있으나 인증과 변경 충돌의 최종 판단을 대신하지 않는다.

## 4. 기존 기능 재사용

모든 기능의 보존을 목표로 하되 실제 source/runtime/API 검증으로 기능 목록을 확정한다.

첫 검토 대상:
- 프로젝트 읽기·검색·파일 편집 및 재편집
- worktree·새 파일·tracked 파일 commit
- Python/Node 테스트와 실행 결과
- GitHub PR/CI/main 동기화
- 선택적 배포·백업·원자적 교체·rollback
- 서비스 상태·controlled restart·health
- RCC 생성·전송·결과 회수·중복 방지
- 진단·복구·기존 Improvement Ledger 연계
- 기존 Laya Shadow 호출 및 fallback

위 목록은 검증 완료 목록이 아니다. 각 기능의 source entrypoint, 운영 경로, 보호 조건, 테스트, 이전 상태를 다음 조사에서 채운다.

기존 전체 gateway를 감싼 것만으로 단순화 완료라 하지 않는다. 초기 호환 연결은 가능하나, 독립 실행 계약을 확인하고 최종 판단 책임을 이관한 경로는 중복된 구형 판단에서 분리한다. 기존 guard를 우회하거나 두 시스템이 같은 변경을 동시에 소유하게 하지 않는다.

## 5. 결과와 복구

하나의 operation_id에 하나의 실제 실행만 허용한다. 재호출은 저장된 결과 또는 확인 중 상태를 반환한다. 응답 유실은 자동 재실행 사유가 아니다.

기존 receipt를 우선 연결하고 로그 전체를 새 저장소로 복제하지 않는다. NOT_APPLIED는 실행 전 거부 증거가 있을 때만 인정한다. 기존 LIVE를 전환할 때는 파일 SHA, 백업, rollback, 필요한 최소 reload 및 실제 acceptance를 확인한다.

## 6. 변경 용이성 acceptance

- 이름 변경: 작업·연결·권한 유지.
- 그룹/역할 변경: 기능적 라우팅만 의도대로 변경, 기술 권한의 암묵적 확대 없음.
- 연결 교체: stale 응답 거부, 기존 작업 기록 보존.
- 실행자 인계: 이전 실행 부재 또는 terminal 결과 확인 후 한 번만 재개.
- 정책 변경: 관련 도구가 같은 버전과 결론을 사용하며 한 번의 조회로 적용 이유 확인.
- adapter 추가: 기존 무관한 adapter 코드와 노드 모델 수정 없이 계약 테스트 통과.
- 실제 개발 작업: worktree → edit → re-edit → test → commit → PR/CI → selective deploy → health/acceptance.

이것은 문서상의 서로 다른 기준을 확인한 것이며 현재 실행 코드의 충돌을 증명하지 않는다. BCT는 논리 신원·인증 주체·연결 주소·UI 연속성의 의미를 각각 명시한다.

현 단계에서 ACT 코드 전수 조사나 기능별 독립 재사용 가능성 검증은 수행하지 않았다. 확정 일정은 첫 end-to-end 경로의 의존성 확인 이후 산출한다.
