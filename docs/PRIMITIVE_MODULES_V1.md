# 원시 모듈 V1 — 정보 확인

상위 명령(체인 메시지, ABA, Manager 승계 등)은 각각의 실행 절차를
새로 정의하지 않는다. 작은 원시 모듈을 순서대로 조합한다.

이 문서는 그 첫 번째 모듈을 고정한다.

## 이름을 읽는 법

흐름을 설계할 때 생각하는 층은 세 개뿐이다. 코드 파일을 뜻하는
`모듈`은 이 표에 넣지 않는다.

```text
원시 부품
  = 한 역할만 수행한다
  = 감시, alarm, wake, 메시지 제출, 영수증 읽기

부분 레시피
  = 원시 부품을 묶어 한 가지 재사용 가능한 결과를 만든다
  = 다른 부분 레시피를 포함할 수 있다
  = 예: Send Delayed Message, 메시지 보내기

전체 레시피
  = 사용자의 목표를 끝까지 수행하는 흐름
  = 예: 1:1 Chain Message
```

공개 명령 이름은 다음 문법을 쓴다.

```text
전체 현재 보기: bct_status 처럼 이름만 쓴다
원시 행동:       bct_동사_명사
부분 레시피:     bct_[수식어_]동사_명사
```

한 기능을 가리키는 짧은 합성어는 임의로 동사 둘처럼 나누지 않는다.
예를 들어 `wakeup`은 하나의 기능 이름이므로 `bct_wakeup_message`로 쓴다.

그래서 `bct_send_message`는 메시지 보내기라는 기본 행동이고,
`bct_send_delayed_message`는 그 행동에 감시·alarm·지연이라는 부분
레시피를 얹은 이름이다. `delayed`는 뒤집힌 대상이 아니라 Send Message를
꾸미는 실행 방식이므로 유지한다.

```text
bct_status
bct_check_conversation_network
bct_send_message
bct_send_delayed_message
bct_cancel_delayed_send
```

기존 뒤집힌 이름(`bct_task_run` 등)은 현재 호출을
깨지 않도록 호환 별칭으로 남기고, 이후 레시피에서는 표준 이름을 쓴다.

### 메시지·탭 부분 레시피의 실제 이름

`bct_send_message`는 메시지 보내기 부분 레시피의 공개 진입점이다. 아래
기존 내부 이름을 바꾸지 않는다.

```text
bct_send_message
  → send-message
     ├─ send-to-tab
     │   = 이미 UUID가 확인된 기존 대화 탭에 전송
     └─ send-to-created-tab
         = BCT가 방금 만든 탭의 create_operation_id로 전송
```

`send-to-created-tab`은 임의로 붙인 표현이 아니다. 새 탭의 대화 UUID를
추측하지 않고, 생성 영수증으로 그 탭을 증명하는 기존 실행 경로의 실제
이름이다.

탭 이동과 닫기도 기존 내부 명령을 그대로 사용하되, 공개 진입점은 동사
우선 이름으로 둔다.

```text
bct_move_tab  → move-tab
bct_close_tab → close-conversation-tab
```

`bct_close_tab`은 정확한 대화 UUID·창·탭·세션을 모두 요구한다. 창 닫기
명령은 현재 이 레시피 체계에 없다.

## 1. 정보 확인 / 현재 보기

```text
현재 보기 = bct_status(scope="bct")
```

모든 조합 흐름은 시작할 때 이 블록을 한 번 실행한다. `scope="node"`를
추가로 실행할 필요는 없다. `scope="node"`는 같은 결과에서 노드 부분만
따로 보는 좁은 보기다.

### 이 블록이 돌려주는 현재 사실

- Core 준비 상태, RCC 연결 상태, 관측 시각
- 현재 열려 있고 RCC가 관측한 모든 노드
  - 노드 번호, 대화 이름, 대화 UUID, 탭/창 연결
  - 활성 여부, 응답 생성 여부, 관측 원천과 시각
  - 대화망(`network`), 역할(`roles`), 담당 작업(`assigned_task`), 노드 메모(`node_memo`)
- 현재 실행/감시/복구와 경고·UNKNOWN·식별 충돌 같은 주의 상태

### 이 블록으로 할 수 있는 판단

- 지금 실제로 열려 있는 노드를 대화망, 역할, 활동 상태 기준으로 정렬한다.
- 작업에 필요한 대상이 현재 있는지 찾는다.
- 이미 진행 중인 흐름, 감시, 경고 때문에 시작을 멈추거나 다음 확인으로 간다.

### 이 블록이 하지 않는 일

- 노드의 소속·역할·메모·담당 작업을 바꾸지 않는다.
- 메시지를 보내거나 AI의 다음 행동을 판단하지 않는다.
- 닫혀 있는 노드까지 포함한 특정 대화망의 전체 구성표를 펼치지 않는다.

특정 대화망 전체 구성표가 필요할 때만 다음 블록을 이어 붙인다.

```text
대화망 확인 = bct_check_conversation_network(project="...")
```

`bct_check_conversation_network`는 대화망을 만들거나 바꾸지 않는다. 현재 노드에 이미
기록된 network/role/assigned_task 정보를 대화망·프로젝트 관점으로 정리하고,
필요하면 등록된 대화망과 권한 있는 프로젝트 문맥을 함께 읽는다. 1:1 체인의
기본 단계에는 넣지 않고, 대화망을 실제로 쓰는 조합에서만 이어 붙인다.

## 사용 규칙

```text
조합 흐름 시작
  → 현재 보기 1회
  → 결과를 이용해 시작 점검·정렬·계획·준비 판단
  → 실제 보내기/깨우기/변경 직전에는 해당 대상의 UUID·탭·현재 상태만 재확인
```

`현재 보기`는 지도를 만든다. 실제 외부 행동은 그 행동 직전의 정확한
대상 확인을 별도 블록으로 요구한다.

## 2. 작업 계획 / 설계도

```text
작업 계획 = 현재 보기에서 판단한 목표와 필요한 구성을 선언한다.
```

이 블록은 메시지를 보내거나 노드를 바꾸지 않는다. 이후의 대화망·노드
준비, 실행 세션, Task Run, Delayed Send가 같은 설계도를 보게 한다.

### 최소 계획 카드

```text
목표
완료 기준

시작 주체: A(Manager)
필요한 역할: 예) Manager 1, Worker 2, 검토자 1
대상 조건: 예) CONFIRMED Worker, "시험 응답" 대화망

실행 계획
  - 작업을 어떤 단계로 나눌지
  - 각 단계에서 어느 Worker에게 무엇을 전달할지
  - 결과를 무엇으로 인정할지

이어가기 계획
  - 무엇을 감시할지
  - 조건이 충족되면 alarm 뒤 무엇을 할지
    (다음 메시지 / 깨우기 / Manager 반환 / 보류)
  - 중단 또는 Manager 판단으로 돌릴 조건

환경 준비 부속 계획  [필요한 경우에만]
  - 이 실행에 기존 대화망이 필요한지
  - 기존 노드로 충분한지 / 새 노드 준비가 필요한지
  - 필요한 대화망 소속·역할·담당 작업 설정은 무엇인지
```

### 계획 블록의 결과

작업 계획은 자유로운 긴 설명으로 끝나지 않는다. 다음 블록이 읽을 수
있도록 아래 네 결과를 반드시 남긴다.

```text
1. 실행 단계
   - 단계 번호, 담당 역할, 전달할 일, 완료 기준

2. 다음 연결
   - 각 단계가 끝났을 때 감시할 조건과 다음 행동
   - 다음 메시지 / 깨우기 / Manager 반환 / 보류 중 하나

3. 환경 준비 요청
   - 준비 없음
   - 기존 노드·대화망 설정 조정 필요
   - 새 노드 준비 필요

4. 보류 이유
   - 계획을 확정할 수 없는 정보나 사용자 판단이 있으면 기록
```

그래서 이후 블록은 계획을 다시 해석하지 않는다.

```text
환경 준비 블록은 3만 읽는다.
Task Run은 1의 현재 단계를 읽는다.
Delayed Send는 2의 다음 연결을 읽는다.
Manager는 4가 있을 때만 새 판단을 한다.
```

### 이 블록의 위치

```text
현재 보기
  → 시작 점검: 지금 계획을 만들어도 되는가?
  → 작업 계획: 목표를 어떤 실행 단계로 끝낼 것인가?
  → 환경 준비 부속 계획: 대화망·노드 조정이 필요한가?
  → 필요할 때만 대화망 확인: bct_check_conversation_network
  → 대화망·노드 준비: 필요한 경우에만 실제 구성을 맞춘다
  → 세션 준비와 Task Run
```

계획은 새 노드를 자동으로 만들지 않는다. 새 노드가 필요하면
`새 노드 준비 필요`라는 계획 결과만 남긴다. 실제 생성과 연결은
별도의 실행 블록이며, 생성된 노드가 `CONFIRMED`가 된 뒤에만
다음 단계의 대상으로 쓸 수 있다.

### 현재 명령과의 연결

현재 `bct_run_plan`은 목표, 완료 기준, 단계, 가정을 저장하는 명령이다.
대화망·역할·감시·다음 행동까지 위 카드처럼 구조적으로 저장하고
검증하는 형식은 아직 없다. 이 문서의 계획 카드는 그 다음 확장의
입력 계약이며, 기존 `bct_run_plan`은 당분간 이 내용을 사람이 읽는
계획 단계로 보관하는 기반으로 쓴다.

## 점검은 두 번으로 나눈다

`필요한 Worker가 CONFIRMED인가?`는 계획이 있어야 답할 수 있다.
따라서 점검을 하나의 거대한 단계로 만들지 않는다.

```text
계획 전 기본 점검
  = 현재 보기를 읽을 수 있는가?
  = Core/RCC가 현재 관측되는가?
  = 이번 흐름과 같은 대상·같은 전달의 UNKNOWN이 있는가?

작업 계획
  = 목표, 실행 단계, 필요한 역할, 다음 행동을 선언
  = 그 결과로 필요한 대화망·노드 준비를 부속 계획에 적음

계획 후 실행 준비 점검
  = 계획에 적은 Manager/Worker가 실제 CONFIRMED인가?
  = 계획의 대화망·역할·담당 작업이 실제 구성과 맞는가?
  = 필요한 새 노드는 준비되고 연결됐는가?
  = 실행 세션과 Work를 시작할 수 있는가?
```

다른 대상의 과거 UNKNOWN, 이미 끝난 감시, 관련 없는 옛 경고는
계획 전 기본 점검의 참고 기록이다. 그것만으로 다음 흐름을 막지
않는다. 같은 대상·같은 전달에 걸린 UNKNOWN만 새 전송을 막고
원래 영수증 확인으로 보낸다.

## 3. A-B 1:1 Task Message 원시 조합

첫 번째 완성 목표는 대화망 분배가 아니다. 이미 준비되어 있고
`CONFIRMED`인 A(Manager) 한 명이 B(Worker) 한 명에게 하나의 실행 흐름을
맡기고, B가 자기 기록을 읽으며 BB를 반복한 뒤 필요할 때만 BA로 반환하는
조합이다.

```text
입력
  A: 정확히 확인된 Manager 노드
  B: 정확히 확인된 Worker 노드
  작업 하나: 지시와 완료 기준
  B 반복 규칙: BB로 이어갈 때와 BA로 반환할 때의 판단 기준

흐름
  1. 현재 보기
  2. 계획 전 기본 점검
  3. 작업 하나의 계획 카드 작성
  4. 실행 세션 준비와 A/B 노드 동기화
  5. B의 다음 응답을 위한 Delayed Send 감시를 먼저 준비
  6. Task Run으로 B 한 명에게 최초 작업 전달: A → B
  7. B가 처리하고, 현재 결과와 다음 판단(BB / BA / 보류)을 기록
  8. B의 응답 완료 뒤 Delayed Send가 그 이전 턴의 판단을 읽고 전달
       - BB: 현재 호환 레시피는 B에게 다음 메시지를 전달
             → 다음 턴 B가 이미 결정된 BB 맥락을 읽고 5부터 반복
       - BA: A에게 결과·반환 맥락을 전달
  9. 각 전달의 영수증과 마지막 반환 결과 확인
 10. A는 BA 반환을 받은 뒤에만 그 실행 흐름 밖의 다음 결정을 함
```

### 이 조합에 포함하지 않는 것

- `bct_get_conversation_network`/`bct_set_conversation_network`을 요구하는 대화망 구성 변경
- 새 ChatGPT 노드의 자동 생성
- 여러 Worker에게 동시 또는 순차로 분배하는 실행기
- B가 현재 맡은 흐름 밖의 새 체인 전체를 만드는 기본 동작

노드에 이미 적혀 있는 network/role/memo는 현재 보기에 남아 있어도
1:1 실행의 필수 입력은 아니다.

### B 재개를 나누는 원시 블록

후속 방향의 판단은 **이전 턴 B가 작업을 끝낸 뒤** 한다. Delayed Send와
다음 턴 B는 그 판단을 다시 만들지 않고, 이미 기록된 판단을 읽고 따른다.

```text
B의 한 턴
  1. 실행 맥락 읽기: 이전 턴이 결정한 BB 지시와 현재 기록 확인
  2. 조건 감시 선준비: 이 턴의 응답이 끝난 뒤를 위해 감시 예약
  3. 작업 처리
  4. 결과 기록
  5. 다음 판단 기록: BB / BA / 보류

BCT 경계 처리
  6. 조건 감시: B 응답 완료와 입력 가능 확인
  7. alarm: 재개 조건 충족 기록
  8. 이전 턴 B의 판단 읽기
  9. 전달: BB면 B에게 다음 메시지, BA면 A 반환
```

따라서 미래의 `웨이크업 메시지`는 다음 턴 B에게 새 판단을 시키는 명령이 아니다. 이미
결정된 BB 실행 흐름의 맥락을 읽고 작업을 시작시키는 신호다.

```text
B가 받을 웨이크업 메시지
  = 실행 흐름 ID와 맥락 위치
  = 다음 작업 방향을 다시 판단하라는 요청이 아님

B가 읽는 실행 맥락
  = 최초 지시·완료 기준·현재 반복 번호·직전 결과·영수증·
    이전 턴이 이미 기록한 BB 지시
```

`현재 보기`와 `실행 맥락 읽기`는 다르다.

```text
현재 보기
  = BCT 전체와 현재 열린 노드들의 지도

실행 맥락 읽기
  = B가 지금 맡은 한 실행 흐름의 작업 기록
```

후자는 B가 재개될 때 필요한 원시 모듈이며, 메시지 본문이나 wake 동작과
분리한다.

### 현재 분리 구현 상태

기존 `NEXT TASK — SELF/MANAGER` 형식은 호환 레시피로 유지한다. 다만
Delayed Send는 이제 응답 본문에서 해석한 이전 턴 B의 결정을 실제 전달
전에 별도로 기록한다.

```text
legacy NEXT TASK 본문
  → BB/BA 결정 기록
  → alarm 기록
  → SELF wake 또는 Manager 반환 전달
```

`실행 맥락 읽기`는 이제 읽기 전용 공개 블록으로 꺼냈다.

```text
실행 맥락 읽기 = bct_execution_context(work_id, task_id, generation=0)
```

- `generation=0`은 가장 최근에 기록된 판단을 읽는다.
- 같은 Work와 같은 담당 epoch에 묶인 기록만 돌려준다.
- 돌려주는 것은 직전 B의 BB/BA 판단, 직전 응답의 증거, 감시 상태와
  정확한 실행 바인딩이다.
- 이 명령은 보내기·깨우기·재판단을 하지 않는다.

`웨이크업 메시지`도 순수 행동 요청으로 분리했다. alarm과 실행 흐름 참조를
입력으로 받아 `wakeup_message(worker, execution_ref)` 요청만 만든다. 이
행동은 SELF/MANAGER 판단을 알지 않으며, 아직 실제 RCC 메시지 전송과도
연결하지 않았다. 따라서 기존 Delayed 센드 메시지의 동작을 유지하면서,
다음 단계에서만 웨이크업 메시지 전달을 최소 맥락 참조로 바꿀 수 있다.

### 현재 실제 명령 경계

현재 소스에는 목적이 다른 1:1 작업 전달 경로와, 메시지 운용을 완성하는
조합 레시피가 있다.

```text
경로 A: Task Run
  준비된 세션 → bct_task_run → Worker 한 명 dispatch
  → Task Run이 자체 영수증을 읽고 결과를 기록

경로 B: Chain Message / Delayed Send
  Delayed Send 감시 선준비 → 정확한 메시지 전송
  → B 응답 감시 → SELF 또는 Manager 반환

조합 C: Task Message
  Manager의 작업·완료 기준·BB/BA 기준 작성
  → Chain Message 선준비·정확 전송
  → Worker의 작은 BB 반복
  → 완료·정체·위험·진전 없음에서 Manager 반환
```

- `bct_task_run`은 준비된 세션에서 Worker 한 명에게 작업 하나를
  dispatch하는 실행 단위다. 현재는 자체 결과 영수증을 기다린다.
- `bct_send_delayed_message`와 `bct_chain_message`는 감시를 먼저
  준비한 뒤 정확한 메시지를 보내는 경로다.
- `bct_task_message`는 한 Manager와 한 Worker 사이에서 사용할 수 있는
  선택형 지시문 봉투다. 기본 `max_rounds=0`은 진전 기반 반복이며, 고정 한도는
  사용자나 Manager가 비용·시간 예산으로 명시할 때만 1~12로 둔다. 양수 한도에서
  Worker가 SELF를 요청하면 요청 증거는 보존하고 실제 경로만 Manager 반환으로
  바꾼다.
- `bct_operation_get`은 전달 행동 하나의 정확한 영수증을 읽는다.
- `bct_status(scope="bct")`는 결과 이후의 전체 현재 보기를 갱신할 때만
  다시 읽는다.

### Task Run과 Task Message의 경계

두 경로를 단순히 연달아 호출하면 같은 작업이 두 번 전송될 수 있다.
따라서 `Task Message`는 전체 Chain Message 안에서 선택적으로 쓸 수 있는
메시지 지시문 부품이며, 준비된 오케스트레이션 세션의 `Task Run`을 내부에서
다시 호출하지 않는다.

```text
Work / 실행 세션 / B의 정확한 대화 UUID·탭 / Task Run·Delayed Send 영수증
```

`Task Run` 영수증과 `Task Message`를 하나의 오케스트레이션 세션으로 묶는
상위 다중 실행 조합은 여전히 별도 과제다. 하지만 사용자가 요청한 자연스러운
1:1 Manager → Worker → 진전 기반 BB → Manager 메시지 흐름에서 `Task Message`는
필요할 때 쓰는 지시문 부품이다. 이를 다중 Worker `Chain Run`으로 부르지 않는다.

## 4. 노드 이상과 교체 조합

노드 복구는 하나의 거대한 자동 명령이 아니다. AI가 상태 증거를 읽고
교체 여부를 판단할 수 있도록 아래 부품과 부분 레시피를 순서대로 조립한다.

```text
Check Node
  = 읽기/관측 부분 레시피
  = 사람이 이상하다고 본 정확한 현재 노드를 읽음
  = 기존 RCC의 DOM 오류·연결·생성·최근 활동과 기존 Task/Operation 변화를 조합
  = OK / WAIT / CHECK 및 원인을 반환
  = Recheck 비교용 최소 스냅샷 외 새 Operation·진단 영수증을 만들지 않음

Recheck Node
  = 비교 부분 레시피
  = 같은 노드를 다시 읽고 이전 최소 스냅샷과 진행 변화를 비교
  = CONTINUE / RECHECK / RESTART를 제안하며 활성 Chain 감시는 같은 신호로 자동 계속

Pause Node
  = 상태 변경 원시 부품
  = 기존 노드의 새 Chain/Delayed Send를 막고 WATCHING/RESERVED를 PAUSED로 변경
  = 계획, 영수증, 정확한 신원, UNKNOWN 기록은 보존

Replace Node
  = 부분 레시피
  = 준비 → 승계 Chain Message → 승계 감시 확인 → commit
  = BCT는 후임을 고르지 않으며, commit 전에는 기존 노드가 계속 PAUSED

Reset Node
  = 마무리 부분 레시피
  = 복구 스냅샷 저장 → 기존 Delayed Send 정리 → 정확한 탭 닫기 → 결과 기록
  = UNKNOWN close는 RESET_UNKNOWN으로 보존하고 새 Operation으로 재시도하지 않음
```

다섯 개를 순서대로 묶은 **Node Recovery**가 전체 레시피다. 공개 명령은
각 경계를 따로 노출하므로 Manager가 증거를 읽고 다음 단계를 선택할 수 있다.

```text
bct_check_node
bct_recheck_node
bct_pause_node
bct_replace_node(action=status|prepare|start|commit)
bct_reset_node(action=status|plan|apply)
```

### 체인 안에서의 위치

```text
정상: A → B → BB ... → BA → A

이상 관측:
  Check Node
    → WAIT/CHECK이면 다음 관측에서 Recheck Node
    → 회복되면 기존 체인 계속
    → 여전히 이상하면 Manager가 Pause Node 결정
      → Replace Node가 후임에게 승계 Chain Message
      → 후임 감시가 실제로 준비된 뒤 commit
      → Reset Node가 이전 노드를 복구 가능하게 정리
      → 후임은 다음 미완료 단계부터 계속
```

`Check`와 `Recheck`의 결과는 관측 증거이지 AI 판단을 대신하는 정책이 아니다.
`UNKNOWN`은 노드 장애의 자동 증거도, 재전송 허가도 아니다. 같은 Operation
영수증과 현재 외부 상태를 먼저 대조한다.
