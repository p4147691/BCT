# PR3-a safe reimplementation (new main after #127)

Built from main `8922d3d7e029d3bcc8879a0bd3cc05cef34a4f4e` without cherry-picking or reusing #126 branch/code. Internal Python adapter; not exposed as MCP, Chrome extension or Native Host capability. The only schema addition is an explicitly initialized completion event table in temporary Store; never auto-migrate a live DB.

**Source evidence:** completion_report and result_get recompute the existing Core canonical digest using `orchestration._digest(json.loads(mailbox.payload_json))`, compare against mailbox.message_digest and the completion event result_digest, and verify event_digest on retrieval. Source session, assignment current_generation, assignment attempt worker, message kind/sender/assignment/generation must match. An event ID is idempotent only for the identical immutable payload.

**Target fencing:** delivery_request checks PR2 immutable outbox and *current* assignment session/generation, attachment active/node/generation. fake_send delegates epoch/token, reservation, send state and no-auto-retry UNKNOWN to PR2; sent is not recipient ACK. Delivery receipts come from PR2 recovery snapshot. PR1 consumer decision atomicity and PR2 lease/outbox/ACK are not reimplemented.

**Recipient evidence:** recipient_ack checks current assignment and active target attachment, immutable payload/command digest, and an explicit `recipient_proof` with exact node/attachment/generation/processed command/ack digest. This proof is *test-scoped data*, not a trusted browser principal or cryptographic authorization. This adapter is **not suitable as a public ACK capability** until a future boundary supplies an independently authenticated recipient identity and real persisted processing evidence. A forged `verified_by=isolated_fake_transport` object cannot establish a real recipient. PR2 does authoritative lease/token and idempotent ACK; the command ID by itself only proves deterministic identity, not execution.

**Proof scope:** only temp SQLite and deterministic fake transport: completion/digest, reopen, duplicate/conflict, stale generation, detached/foreign proof, wake/decision/outbox, pre-send abort, post-send UNKNOWN, epoch/token fence, DELIVERED separate from ACKNOWLEDGED. No real browser or Chrome DOM, HKCU, Native Host registration, live Core/token, RCC, Issue #111, existing UNKNOWN/Claim/consumed_at, merge or deploy. An actual Chrome E2E requires separate approval, protected staging, authenticated session/node/recipient principal, trusted completion observation and signed/verified recipient process evidence with rollback.

**ACK atomicity:** PR3-a holds one Store BEGIN IMMEDIATE write transaction from current attachment/assignment fencing through the existing PR2 acknowledge_delivery state transition. PR2 accepts the internal transaction connection and rechecks current target in that same transaction; its lease, epoch, outbox, and ACK state machine are unchanged. Race-injection tests mutate attachment/assignment after PR3-a verification but before PR2 transition, and verify ACK is not persisted. This remains fake-only recipient proof, not authenticated browser identity.
