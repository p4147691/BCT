# PR3-b — isolated internal capability authorization

Base main: `ddda61b2ca19e5f99cc2a7fe298bb2e608ca6297`. Internal Python-only functions. **No HTTP, MCP, listener, Chrome, Native Host, profile or registry entry is created.**

`install_schema` explicitly creates two additive tables in test Store; this change does not migrate LIVE databases. `issue_fake_grant` is **test-fixture-only**, not a production issuance authority. It returns an ephemeral random 256-bit credential to the test caller; only SHA-256 digest is persisted in SQLite, never plaintext. Errors do not include credential or secret contents. Callers must never log raw credentials. HMAC constant-time comparison is used for credential digest equality after indexed lookup; this does not substitute secure transport or credential provisioning.

Grants bind exactly one session ID, node ID, attachment ID and generation, capability operation, Origin `chrome-extension://acdgnmbgpkfjkckccbhmccojgigbfcge/`, and audience `bct-bridge-core-internal-v1`, plus expiration and explicit revocation state. Each `request_id` (nonce) is persistently reserved with a digest of canonical scope and arguments: reused same request is rejected; different arguments under the same request ID are a conflict. The same grant may authorize different unique request IDs before expiry or revocation, never broader operations. Authorization requires a currently active exact attachment/node. Failed downstream Core operations do not grant a right to automatically retry or resend effects. A future endpoint must establish authenticated provenance of Origin and caller rather than trust caller-supplied strings.

`call` gates PR3-a `completion_report`, `result_get`, `delivery_receipt_get`, and `recipient_ack`. PR1 consumption receipt/decision and PR2 lease, immutable outbox, and ACK remain authoritative; current source/target Core fencing is not bypassed. A caller-constructed `recipient_proof` remains fake-only and cannot be promoted into authenticated browser processing evidence.

**Not yet proved:** real extension-ID and process identity attestation, secure key storage and rotation, TLS/IPC peer binding, authenticated endpoint and rate limits, browser-to-Core authorization issuance, recipient process evidence and persisted command execution ACK. Actual Chrome E2E requires separate approval and exact isolation/rollback. No production token or Core is generated here.

Audit corrections: result_get now checks returned RESULT session against grant session; authorization expiry uses trusted internal time.time() (caller now is ignored, including NaN/past inputs). Fixture issue_fake_grant refuses stores outside a specifically named ephemeral temporary fixture path. Production issuance still requires an independent hardened authority; a temporary-path heuristic is only a test guard, not a production trust boundary. Fake recipient proof remains fake-only.
